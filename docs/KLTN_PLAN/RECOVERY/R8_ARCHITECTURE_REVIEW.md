## 3. Why A02 is not recommended

R7 §6 is explicit about reuse and adds real constraints; it is materially better than hiding identifiers in arbitrary JSON. The remaining objection is **responsibility and verification cost**, not the names of the tables alone. Changing Prisma model names with `@@map` would not remove that cost.

AgentExecution has an Agent goal, provider usage/costs, human wait, fallback and evaluation relations. A business operation has an authenticated command identity, atomic effects and replay result, including commands with no stock movement and no model call. Their time/state/retention semantics differ. A stock-count approval must still work if no Agent workflow is deployed; a legacy Agent log import must not affect confidence in financial deduplication.

R7 then makes AgentToolCall hold TOOL, APPROVAL, PROPOSAL_LINE, VERSION_BINDING and LEGACY rows. One nullable column set must enforce multiple mutually exclusive schemas; metadata uses ToolCallStatus.SKIPPED and stepNo stops meaning dispatch order. New dispatchNo exists to repair that ambiguity. Generic version targets and root/child result FKs broaden the schema further. This is a small generic workflow framework embedded inside the Agent model, with all business modules depending on its tags and transition logic.

Consequences to test include: an approval line counted as a dispatch; a generic edit accepted under an Agent approval transition; a legacy row escaping new checks; a count result depending on a mutable Agent record; and a provider reconciliation state colliding with synchronous command completion rules. Constraints can address individual cases, but every new operation/subtype expands the combinations and migration surface. A dedicated BusinessOperation still needs careful result/subject constraints; it does not solve races by itself. It does remove tool/provider/budget state from the journal and gives those invariants one coherent owner.

Do not “fix” this objection by storing generic operations in SystemSetting, AgentLog, backup-schema tables, fake ledger movements or a renamed unconstrained JSON document. Likewise, a generic record is not inherently unsafe if deliberately designed as the system's workflow engine; that would be a larger explicit architecture commitment with its own requirements/evaluation, not a cheap27-table optimization for this project.

## 7. Enforcement that remains necessary under either table count

Keep row-local ranges, exact units/scale, nonnegative physical/reserved values, reserved≤physical, typed ownership FKs, immutable identifiers and partial uniqueness close to the data. One allocation terminal across RELEASE/CONSUME, unique operation scope/type/key and one applied order settlement are database invariants, not optimistic service checks. Expected-version updates must affect exactly one row.

Use a protected stock transaction boundary for reserve/release/consume/receipt/count/waste/return. It re-reads balances and current principal, locks the complete ingredient/batch set in the approved common order, updates caches/versions, inserts genuine movements and stores the operation outcome atomically. Narrow deferred checks can verify final cross-row sums; the revision must state which function owns each write and which check catches bypass. Avoid duplicate independently maintained implementations of the full recipe engine in a generic JSON trigger and the API. Where independent recomputation is necessary, give it a domain-specific contract and test both against fixed vectors; it is not eliminated just to reduce SQL.

Retain exact Decimal/rational arithmetic, ingredient dimensions, whole pieces, café expiry policy, FEFO ranking, no automatic reservation timeout, explicit item-start consumption, separate refund/loss classification and current-role checks. All stock writers must comply; a legacy “temporary” side door cannot remain enabled at cutover. Operation lookup rechecks authorization before returning any retained result. These requirements do not change with the physical table choice.

Do not use new enum labels/types just to accommodate the review. Under the proposed dedicated alternative, BusinessOperation and AgentApproval can use explicitly checked TEXT state sets and finite transition constraints, subject to revised contract review; existing16 PostgreSQL ENUM types/labels remain unchanged. Checked TEXT still requires validation/versioning and is not a substitute for meaningful ownership.
