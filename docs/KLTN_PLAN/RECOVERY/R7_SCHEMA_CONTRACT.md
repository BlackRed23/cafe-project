## 3. Count, type and relation conventions

Retained 27 business tables: **User, Category, Product, Ingredient, IngredientBatch, InventoryTransaction, StockCount, StockCountItem, Recipe, RecipeIngredient, Topping, ToppingIngredient, Order, OrderItem, OrderItemTopping, Supplier, SupplierIngredient, PurchaseRequest, PurchaseRequestItem, GoodsReceipt, Payment, PaymentCallback, PaymentReconciliation, AgentExecution, AgentToolCall, AgentEvaluation, SystemSetting**. Intended transitional retirement is Inventory, InventoryBatch, SupplierProduct, AgentLog, only after separately approved preservation/cutover. This is a target inventory, not authorization to drop them. Backup artifacts and Prisma migration metadata are not business tables and cannot be used to hide runtime business state.

Keep the existing 16 enum types and labels: UserRole, CategoryKind, InventoryTransactionType, WasteReason, StockCountStatus, OrderStatus, ConsumptionStatus, PaymentStatus, PaymentMethod, TransactionStatus, CallbackStatus, ToppingType, PurchaseRequestStatus, GoodsReceiptStatus, ExecutionStatus, ToolCallStatus. **No new ENUM type or label** is proposed. New discriminators use bounded TEXT + named CHECK constraints; this increases constraint complexity and must be accepted explicitly, not counted as a new PostgreSQL enum.

Dictionary notation: `!` = NOT NULL, `?` = nullable, `T` = TEXT, `I` = INTEGER, `B` = BOOLEAN, `V` = BIGINT, `TS` = TIMESTAMPTZ(3), `Q` = NUMERIC(14,3), `U` = NUMERIC(18,4), `M` = NUMERIC(14,2), `H` = CHAR(64) lowercase SHA-256 hex with CHECK `^[0-9a-f]{64}$`. IDs are opaque nonempty trimmed T, generated server-side; don't parse concatenated IDs. All unspecified added fields default NULL; `!` fields require explicit values unless a default is listed. Existing fields not named for change retain their meaning/type. No silent money widening: the M fields explicitly replace existing smaller order-item cost totals; item sale price remains NUMERIC(12,2), with overflow rejected before writes. API decimals are canonical strings; quantities cannot exceed declared capacities; pieces must be integral.

Every FK added here is indexed on its referencing columns, `ON DELETE RESTRICT ON UPDATE RESTRICT`, unless explicitly stated otherwise. Replace cascades on retained recipe/order/approval/payment history with RESTRICT. `UNIQUE(id, ownerId)` additions support listed composite FKs; their redundancy with id PK is intentional. Parent ownership checks not expressible as FK require the named deferred constraint triggers below. All comparisons/checks must use explicit NULL branches or `IS NOT DISTINCT FROM`; SQL UNKNOWN must never accidentally satisfy a critical tagged-row condition. New live records use contractVersion=1; pre-cutover rows are explicitly LEGACY/unverified and cannot enter new write workflows until mapped. No LEGACY flag may exempt new records.

SQL-only partial indexes, exclusion constraints and deferred triggers must be kept in reviewed migration SQL plus a parity manifest, not lost by Prisma regeneration. Prisma must declare all supported scalar/composite relations; raw SQL handles the remaining enforcement. R7 supplies the target contract, not executable migration SQL or a proof of its implementation.

JSON cannot introduce an allocation, approval, actor, source version, provider identity or business subject. On replay, return the exact committed projection after current authorization, even if current business rows changed; never rebuild an old response from mutable live rows. Large result size limits need an API protocol value before implementation; do not truncate a committed response and still claim full replay.

BUSINESS effects/root hash/result commit atomically; a root created for a synchronous transaction cannot be left RUNNING at commit. A successful no-op/zero-variance operation may be SUCCEEDED with zero child movements. Rejected domain operations may persist a terminal REJECTED response only with zero effects. Validation/auth failures need not allocate keys. Concurrent same key waits on unique identity, then same hash returns committed result; changed hash→409 without altering it. Agent parent runs can persist RUNNING/WAITING_APPROVAL; their child BUSINESS executions retain atomicity. External provider dispatch is outside DB atomicity: outcomeUncertain=true plus RUNNING/pending reconciliation blocks retry; no claim that this is an outbox. PR_SEND/provider/refund methods remain disabled until a separate durable dispatch/lookup contract is reviewed. Max3 confirmed-rollback attempts; unknown commit is looked up on authoritative storage before re-execution. Retain keys/results/references for retained business history; payload PII retention needs separate review.

## 8. S05 — inventory invariants and transactional enforcement

All live InventoryTransaction rows have actor, Ingredient, IngredientBatch, execution and deterministic unique key. Do not use referenceType/referenceId as authoritative relationships; retain them only as legacy/display metadata. Batch/item/count/receipt/reversal relationships are typed FKs. No new movement may carry productId/legacyBatchId. Historical unmapped records retain contractVersion=0 with preserved old attribution and are excluded from new operation eligibility; they are not asserted to reconcile until mapping completes.

| Type | quantity semantics (new v1) | Required refs / effect / prohibitions |
|---|---|---|
| IMPORT | positive Q magnitude | GoodsReceipt and batch receipt/item ownership required; physical +=q, reserved unchanged; opening-balance/count discoveries use ADJUSTMENT, not invented supplier receipt |
| RESERVE | positive Q magnitude | item + snapshotIngredient mandatory, allocationId NULL; physical unchanged, reserved +=q |
| RELEASE | positive Q magnitude | allocationId mandatory and identical ownership/amount; reserved -=q only |
| CONSUME | positive Q magnitude | allocationId mandatory and identical ownership/amount; physical -=q, reserved -=q; only eligible batch at explicit item start |
| ADJUSTMENT | signed nonzero Q | stockCountItemId mandatory for count; otherwise separately authorized adjustment operation not present in v1 allowlist, so disabled. physical +=q; cannot fall below open reservations; reason mandatory |
| WASTE | positive Q magnitude | physical -=q, reserved unchanged; WasteReason EXPIRED/DAMAGED/STAFF_ERROR as applicable, free identified stock only; never post-start drink cancellation double decrement |
| RETURN | positive Q magnitude | ADMIN supplier return, physical -=q only; require reversalOfId→original receipt IMPORT, same ingredient/batch and cumulative return≤import qty; no positive return-to-stock of prepared ingredients |
| ORDER/CANCEL/DAMAGE/SIMULATE_SALE | preserved enum labels | Disallowed for new Ingredient ledger; historical only. Simulation writes disabled at cutover until separately specified against the same invariants |

`CHECK movement_shape` and deferred `CT_allocation_owner`, `CT_receipt_attribution`, `CT_count_variance`, `CT_operation_shape`, `CT_operation_request`, `CT_operation_result`, `CT_stock_balance` are required, not optional TODO replacements for business correctness. In addition to batch ownership FK, terminals use composite `(allocationId,batchId,ingredientId,orderItemId)` FK to the RESERVE tuple, with trigger requiring anchor type. REQUIRE non-null item on all reserve/terminal rows so composite FK NULL semantics cannot bypass it. snapshotIngredientId must equal anchor. Physical stock derives from received/opening/adjustment/waste/return/consume movements; reservation movements are not physical movement totals. Zero movement forbidden; zero requirement/count variance stays in snapshot/count tables.

Mutation functions must acquire/re-read complete affected sets, then perform conditional version/status updates and assert exactly one affected row. Common order: claim/lookup root operation identity first (no stock effects); Ingredient IDs in binary ascending order; IngredientBatch IDs in binary ascending order; remaining dependent rows by fixed table order **Category, Product, Recipe, RecipeIngredient, Topping, ToppingIngredient, Supplier, SupplierIngredient, PurchaseRequest, PurchaseRequestItem, GoodsReceipt, StockCount, StockCountItem, Order, OrderItem, OrderItemTopping, Payment, PaymentCallback, PaymentReconciliation, AgentExecution, AgentToolCall, User**, then ID ascending within each. All functions touching both inventory and those parents must use this order; pure catalog/auth updates must not subsequently enter stock mutation in reverse. Read involved IDs optimistically, lock, revalidate ownership/version and abort/restart if the set changed; never acquire a newly discovered lower-order lock late. Publication uses Product lock without later stock writes. Foreign-key locking and constraint-trigger behavior need explicit deadlock tests; the ordering is a specification, not a proof that current writers comply.

Cache changes increment Ingredient and batch versions in the same transaction; opening/retirement/correction handlers cannot bypass them. Deferred triggers validate affected sums at commit under already-held Ingredient/batch locks. State transitions (item pending→committed/voided, allocation terminal, receipt draft→confirmed, count pending→completed) use conditional expected version/status, audit actor and operation ID. New application runtime role must have no unrestricted DML on these protected tables; only reviewed mutation functions may write them. Role/function/search_path/owner configuration is a future separately authorized implementation, not changed here. Privilege enforcement is part of acceptance; application conventions alone are insufficient.

Current identity is rechecked under an appropriate User lock at the authorization point and retained until commit; role/disable writers follow compatible locking and increment authVersion. Server-verified actor is passed to the mutation boundary; a caller-supplied user ID/session variable by itself is not proof of identity. Authentication/DB trust boundary must be reviewed before exposing functions. Inventory functions do no external HTTP/provider work inside transactions. Best-effort read-only post-commit scans remain separate; email/payment send is not automatically retried.
